 # Архитектура simple-agent

Документ описывает целевую архитектуру и дорожную карту. Ключевые решения
зафиксированы в ADR (см. `docs/adr/`). README отвечает на вопрос «как запустить»,
этот файл — на вопрос «как устроено и куда расти».

## Принципы

1. **Headless core.** Ядро (`src/core/`) не пишет в stdout/stderr и ничего не знает
   о CLI. Снаружи ядро — это `Agent.run(): AsyncGenerator<AgentEvent, string>`.
   Любой клиент (CLI, VS Code extension, desktop, web) подписывается на события.
2. **Протокол как контракт.** `src/protocol/` — единственные типы, которыми
   обмениваются ядро и клиенты. Только типы, ноль рантайм-логики, ноль импортов
   из `core/`. Именно этот пакет будут импортировать будущие приложения.
3. **Расширение без модификации (open/closed).** Новый инструмент = один файл +
   одна строка в `builtin/index.ts`. Новый провайдер = один файл + одна строка в
   `providers/index.ts`. Существующий код при расширении не трогаем.
4. **DI через конструкторы.** Единственное место, где создаются конкретные
   реализации, — composition root (`src/index.ts`). Никаких DI-фреймворков.
5. **Провайдер-нейтральная история.** Внутренний формат `Message` не повторяет
   формат конкретного API; каждый провайдер мапит его в свой wire-формат.

## Слои и границы

```
src/
├── index.ts          # composition root: парсинг флагов, сборка приложения
├── protocol/         # контракт core <-> клиенты (будущий пакет @agent/protocol)
│   ├── types.ts      #   ToolCall, ToolResult, TokenUsage
│   ├── events.ts     #   AgentEvent — всё, что ядро сообщает клиенту
│   └── commands.ts   #   команды ядру (run_task, cancel_task)
├── core/             # движок (будущий пакет @agent/core)
│   ├── agent/        #   цикл агента + провайдер-нейтральная история сообщений
│   ├── llm/          #   LLMProvider, реестр провайдеров, providers/deepseek.ts
│   ├── tools/        #   defineTool (zod), ToolRegistry (источники), ToolContext, builtin/
│   └── config/       #   слоистый конфиг с zod-валидацией
└── cli/              # клиент №1: REPL (repl.ts) + рендер событий (render.ts)
```

Правила границ (соблюдаем строго, это дешевле любого линтера):

- `protocol/` не импортирует ничего из `core/` и `cli/`.
- `core/` не импортирует `cli/`; ядро сообщает наружу только через `AgentEvent`.
- `cli/` работает с ядром только через `Agent` и события — никаких «залезть
  внутрь и прочитать messages».
- Конкретные реализации (провайдер, реестр инструментов) создаются только в
  `index.ts`.

## Протокол

События (`AgentEvent`):

| Событие | Когда | Полезная нагрузка |
|---|---|---|
| `text` | модель выдала текст целиком (не-стриминг; между вызовами инструментов или финальный) | `text` |
| `text_delta` | инкрементальный чанк текста при стриминге. Контракт: текст приходит **либо** одним `text`, **либо** серией `text_delta` — никогда оба для одного сообщения | `delta` |
| `tool_call` | модель запросила инструмент | `call: ToolCall` |
| `tool_result` | инструмент отработал (успех или `isError`) | `call`, `result` |
| `usage` | после каждого вызова LLM, если провайдер отдаёт статистику | `TokenUsage` |
| `done` | задача завершена | `answer` |

Команды (`AgentCommand`): `run_task`, `cancel_task` (отмена подключается в фазе 2).

Подтверждения (ADR 0005) — **не** события: когда политика режима требует
спросить пользователя, цикл блокируется на клиентском callback'е
`ApprovalHandler` (`(ApprovalRequest) => Promise<ApprovalDecision>`).
Без handler'а (неинтерактивный запуск) вызовы, требующие подтверждения,
автоматически отклоняются; отказ уходит модели как обычный `tool_result`
с `isError`. Режимы-пресеты: `safe` (спрашивать write+exec), `work`
(только exec), `free` (не спрашивать ничего, опасно); чтения разрешены
всегда.


Фатальные ошибки (сбой API и т.п.) библиотека **бросает** исключением; headless
сервер (фаза 4) сериализует их в error-события на транспорте.

## Модель доставки (как один движок обслужит четыре клиента)

- **CLI и VS Code extension** — оба на Node.js, встраивают `core` как библиотеку
  напрямую (in-process).
- **Desktop и web** — подключаются к тому же `core`, запущенному как
  headless-процесс (stdio / WebSocket, JSON-поток команд и событий). Сервер —
  тонкая транспортная обёртка над библиотекой, а не вторая реализация (фаза 4).

Когда появится второй клиент (фаза 5), репозиторий механически превращается в
монорепо: `packages/core`, `packages/protocol`, `apps/cli`, `apps/vscode`,
`apps/desktop`, `apps/web`. Границы уже проведены — это перенос папок, а не
рефакторинг.

## Дорожная карта

- **Фаза 1 — фундамент (сделано).** Событийный core; `ToolRegistry` с источниками
  и zod-валидацией; реестр провайдеров; слоистый конфиг.
- **Стриминг (сделано, ADR 0004).** Токен-стриминг LLM: событие `text_delta`,
  опциональный `LLMProvider.chatStream` со склейкой tool_call-дельт внутри
  провайдера и фолбэком на `chat()`; живой рендер событий в CLI.
  Kill-switch: `streaming: false` / `AGENT_STREAMING=0` / `--no-stream`.
- **Фаза 2 — надёжность (частично сделано).** Permissions (сделано, ADR 0005):
  режимы `safe`/`work`/`free` над матрицей `ToolKind`, подтверждение через
  клиентский `ApprovalHandler`, отказ как `tool_result`, auto-deny в
  неинтерактивном запуске; тесты матрицы и цикла с fake-провайдером.
  Осталось: retry/backoff и таймауты LLM; отмена задачи (`AbortSignal`
  сквозь цикл и `run_command`); сессионный allowlist («разрешать всегда»).

- **Фаза 3 — память.** Подсчёт токенов и бюджет контекста (`capabilities.maxContextTokens`),
  усечение больших tool-результатов, компакция истории; персистентные сессии
  (JSONL) с resume/fork.
- **Фаза 4 — экосистема.** MCP-клиент как `ToolSource` (неймспейсинг
  `mcp__server__tool` уже заложен в реестре); headless server по протоколу;
  сабагенты (изолированный контекст для подзадач).
- **Фаза 5 — клиенты.** Монорепо; VS Code extension; desktop (Tauri); web.

## Как добавить

### Инструмент

1. `src/core/tools/builtin/myTool.ts`:
   ```ts
   export const myTool = defineTool({
     name: "my_tool",
     description: "What it does (the LLM reads this)",
     kind: "read",
     schema: z.object({ path: z.string().min(1).describe("...") }),
     async execute({ path }, ctx) {

       return { content: "..." };
     },
   });
   ```
2. Одна строка в `src/core/tools/builtin/index.ts`.

Валидация входа — автоматически (zod); ошибка валидации уходит модели как
`ToolResult`, цикл не падает.

### Провайдер

1. `src/core/llm/providers/myProvider.ts`: класс `implements LLMProvider`
   (`id`, `capabilities(model)`, `chat(params)`) + фабрика, читающая свои
   env-переменные (`MYPROVIDER_API_KEY`) и падающая на старте с понятной ошибкой.
2. Одна строка `registerProvider("myprovider", createMyProvider)` в
   `src/core/llm/providers/index.ts`.
3. Пользователь выбирает: `AGENT_PROVIDER=myprovider` или `provider` в
   `agent.config.json`.

## Конфигурация

Слои по возрастанию приоритета: **defaults схемы < `agent.config.json` в cwd <
переменные окружения < CLI-флаги**. Валидация — zod (`core/config/config.ts`),
невалидный конфиг падает на старте с читаемым списком проблем. Ключи API в
схеме конфига нет — ими владеют фабрики провайдеров.
