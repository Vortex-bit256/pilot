# ADR 0003: Реестр провайдеров с фабриками и capabilities

- Статус: принято, реализовано в фазе 1
- Дата: 2026-08-06

## Контекст

DeepSeek был зашит в `index.ts`: конструктор вызывался напрямую, ключ читал
общий конфиг. Планируются другие провайдеры (Anthropic, OpenAI, локальные
модели). Нужно: выбор провайдера конфигом, добавление провайдера без правок
существующего кода, явное владение credentials.

## Решение

1. **`LLMProvider`**: `id`, `capabilities(model)`, `chat(params)`.
   `capabilities` (`streaming`, `toolCalling`, `reasoning`, `maxContextTokens`)
   позволяют ядру и UI адаптироваться к модели (фазы 3–4 будут опираться на
   `maxContextTokens` и `streaming`).
2. **Реестр фабрик** (`core/llm/registry.ts`): `registerProvider(id, factory)`,
   `createProvider(id)`. Выбор — `AGENT_PROVIDER` / `provider` в конфиге.
3. **Фабрика владеет своими env-переменными** (`DEEPSEEK_API_KEY`,
   `DEEPSEEK_BASE_URL`) и валидирует их при создании — ошибка на старте,
   с инструкцией как починить. Общий конфиг про ключи не знает.
4. **Провайдер-нейтральный `Message`** остаётся жёстким правилом: маппинг в
   wire-формат — только внутри провайдера.

## Последствия

**Плюсы:** добавление провайдера = один файл + одна строка; неизвестный
провайдер в конфиге — ошибка со списком доступных; ключи разных провайдеров
не пересекаются.

**Минусы:** реестр — модульный синглтон (мутабельное глобальное состояние);
приемлемо, т.к. заполняется один раз в composition root.

## Альтернативы

- **`switch` по имени провайдера в `index.ts`** — отвергнуто: нарушает
  open/closed, раздувает composition root.
- **Единые `LLM_API_KEY` / `LLM_BASE_URL` для всех провайдеров** — отвергнуто:
  конфликты имён при нескольких провайдерах, менее явные сообщения об ошибках.
- **DI-фреймворк (tsyringe и т.п.)** — отвергнуто: избыточно для одной карты
  фабрик, вредит читаемости.
