# ADR 0002: Реестр инструментов с источниками и zod-схемами

- Статус: принято, реализовано в фазе 1
- Дата: 2026-08-06

## Контекст

Инструменты были статическим массивом; вход — `Record<string, unknown>` с
ручными проверками в каждом инструменте (дублирование, рассинхрон с JSON
Schema, который видит модель). В будущем MCP-серверы будут добавлять и
удалять инструменты динамически, а имена внешних инструментов должны
неймспейситься, чтобы не конфликтовать с builtin.

## Решение

1. **`defineTool` + zod.** Одна zod-схема на инструмент: из неё генерируется
   JSON Schema для LLM (`z.toJSONSchema`) и типизируется вход `execute()`.
2. **`ToolRegistry` с источниками (`ToolSource`).** `builtin` или
   `{ type: "mcp", server }`. Имена для LLM: builtin — как есть, MCP —
   `mcp__<server>__<tool>`. Конфликт имён — ошибка при регистрации.
3. **Валидация в реестре.** `execute()` делает `safeParse`; ошибка валидации
   возвращается модели как `ToolResult` (цикл не падает, модель исправляется).
4. **`ToolContext`** (`cwd`, `signal`) пробрасывается в каждый вызов — точка
   роста для logger/permissions без смены сигнатур.
5. **`kind: read | write | exec`** — метаданные для системы permissions (фаза 2).

## Последствия

**Плюсы:** добавление инструмента = один файл + одна строка; MCP-клиент (фаза 4)
подключается как новый источник без изменений ядра; ручная валидация исчезла.

**Минусы:** зависимость от zod; на границе реестра тип схемы стирается
(`AnyTool = Tool<any>`) — типобезопасность полная в точке определения,
ослабленная внутри реестра.

## Альтернативы

- **Рукописные JSON Schema + ручная валидация** — отвергнуто: многословно,
  схема и валидация расходятся.
- **valibot / arktype** — отвергнуто: zod выбран за распространённость и
  нативный `z.toJSONSchema` (v4) без дополнительных пакетов.
- **Плоский массив инструментов без источников** — отвергнуто: не поддерживает
  динамическое подключение/отключение MCP-серверов и неймспейсинг.
