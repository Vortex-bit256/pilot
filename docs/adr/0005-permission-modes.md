# ADR 0005: Режимы разрешений и канал подтверждения

- Статус: принято, реализовано
- Дата: 2026-08-06

## Контекст

Агент умеет изменять файлы (`write_file`, `edit_file`) и запускать
shell-команды (`run_command`) — до этого ADR всё выполнялось без спроса.
Пользователь должен контролировать необратимые действия, но спрашивать про
каждый `read_file` бессмысленно: чтение не меняет мир, а поток промптов
приучает жать «y» не глядя. Задел существовал: `ToolKind` (`read`/`write`/
`exec`) в `ToolDefinition` (заложен в фазе 1 именно для этого).

## Решение

1. **Движок политик + пресеты.** `PermissionMode` = `safe` | `work` | `free`
   — пресеты над матрицей «режим × kind»: safe спрашивает write+exec, work —
   только exec, free — ничего. Чтения авто-разрешены во всех режимах.
   Матрица — чистая функция `needsApproval(mode, kind)` в
   `core/agent/permissions.ts`, покрыта тестами.
2. **Канал подтверждения — callback, не событие.** `ApprovalHandler =
   (ApprovalRequest) => Promise<ApprovalDecision>` внедряется в `Agent`
   через `setApprovalHandler()`. Протокол событий остаётся односторонним:
   подтверждение — это request/response между ядром и клиентом, а не
   `AgentEvent`. In-process клиенты (CLI, VS Code) показывают промпт;
   headless-сервер (фаза 4) обернёт тот же callback в request/response по
   транспорту без смены семантики ядра. Типы (`ApprovalRequest`,
   `ApprovalDecision`, `PermissionMode`, `ToolKind`) живут в `protocol/`.
3. **Отказ — обычный ToolResult.** Отказ пользователя возвращается как
   `{ isError: true, content: "The user denied…" }` и уходит модели как
   `Error: …` — цикл не падает, модель видит отказ и может скорректировать
   план. Новых типов событий не введено.
4. **Fail-safe.** Нет handler'а (неинтерактивный stdin, headless) — вызов,
   требующий подтверждения, автоматически отклоняется с понятным
   сообщением модели. Исключение в handler'е = отказ. Сломанный канал
   подтверждения никогда не становится разрешением.
5. **Конфигурация.** `permissionMode` в `agent.config.json`, `AGENT_MODE`,
   флаги `--mode/-m` и `--yes/-y` (алиас free). Переключение на лету —
   командой `mode <name>` в REPL (`setPermissionMode`). Режим free при
   старте и при включении печатает красное предупреждение.
6. **CLI-промпт с превью.** `cli/approval.ts` показывает, что именно
   подтверждается: diff для write_file/edit_file (свой LCS-diff по строкам,
   `cli/diff.ts`), команду для run_command, JSON для остального. Промпт
   использует тот же readline-интерфейс REPL через `rl.question()` — ответ
   не попадает в основной цикл ввода.

## Последствия

**Плюсы:** агентом безопасно пользоваться по умолчанию (safe); политика —
чистая функция, легко тестировать и расширять (например, сессионным
allowlist'ом «разрешать всегда»); клиенты не обязаны реализовывать канал —
деgradation в auto-deny корректна; протокол событий не усложнён.

**Минусы:** approval-события не видны в потоке `AgentEvent` (клиент узнаёт
о подтверждении только косвенно, по `tool_result` с отказом); CLI-превью
знает схемы аргументов конкретных builtin-инструментов — новые инструменты
получают сырой JSON-превью, пока их не добавят в `printPreview`.

## Альтернативы

- **Подтверждение событием `approval_request` + ответ через `next()`**
  генератора — отвергнуто: обязывает каждый рендерер заниматься корреляцией
  запрос–ответ и смешивает уведомления с диалогом; callback проще для
  in-process клиентов и так же сериализуем на транспорте.
- **Спрашивать и про read-инструменты в safe** — отвергнуто: чтение
  без побочных эффектов; лишние промпты разучивают пользователя читать их.
- **Deny-list опасных команд (rm -rf /, sudo) поверх режимов** — отложено:
  добавим вместе с сессионным allowlist'ом; матрица режимов этого не
  исключает.
