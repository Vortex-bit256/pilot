# ADR 0006: Отмена задачи и сессионный allowlist

- Статус: принято, реализовано
- Дата: 2026-08-06

## Контекст

После ADR 0005 агент спрашивает разрешения, но запущенную задачу нельзя
остановить: если модель пошла не туда или `run_command` повис, единственный
выход — убить процесс и потерять историю сессии. Кроме того, в режиме safe
однообразные подтверждения одного и того же инструмента утомляют — нужен
«разрешить всегда» в рамках сессии.

## Решение

**Отмена.**

1. `Agent.run(input, { signal })` — клиент передаёт `AbortSignal` на задачу.
   Сигнал идёт вглубь: `ChatParams.signal` → HTTP-слой провайдера (openai SDK
   принимает `signal` вторым аргументом `create()`), `ToolContext.signal` →
   `exec` в `run_command` (задел фазы 1). Цикл проверяет `signal.aborted`
   между итерациями и вызовами инструментов; исключения от абортнутых
   вызовов ловятся и трактуются как отмена, а не как ошибка.
2. Протокол: новое терминальное событие `cancelled` (вместо `done`).
   Частичный вывод, если был, уже доставлен `text`/`text_delta`.
3. **Консистентность истории.** Отмена после того, как assistant-сообщение с
   tool calls уже записано, оставила бы «висячие» вызовы без tool-ответов —
   chat API отклоняют такую историю на следующей задаче. Перед эмиссией
   `cancelled` цикл дописывает tool-сообщения «cancelled by user» на все
   неотвеченные вызовы (`settlePendingToolCalls`).
4. CLI: REPL держит `AbortController` на задачу; **Esc или Ctrl+C** во время
   работы — отмена (Ctrl+C на пустом промпте — прежний hint про выход).
   Промпт подтверждения получает тот же сигнал в `ApprovalRequest.signal`:
   `rl.question(query, { signal })` молча отменяется, обёртка резолвит ""
   (= отказ), цикл завершает задачу через сигнал. One-shot режим не
   обрабатывает Ctrl+C — процесс просто умирает, как у обычной CLI-утилиты.

**Сессионный allowlist.**

5. `ApprovalDecision` расширено значением `"always"`: ядро разрешает вызов
   и запоминает инструмент в `sessionAllowlist: Set<string>` — до конца
   сессии этот инструмент не спрашивается (в пределах текущего режима;
   read не спрашивается всегда). CLI-промпт стал `[y]es / [n]o / [a]lways`.
   Список живёт в памяти процесса и не персистится — осознанно: «вечные»
   разрешения — отдельная история с аудитом.

## Последствия

**Плюсы:** задачу можно прервать в любой точке (стрим, запуск команды,
промпт подтверждения) без потери сессии; история остаётся валидной для API;
`cancel_task` в протоколе теперь имеет реальную семантику для headless-
транспорта фазы 4. Allowlist убирает основной раздражитель safe-режима.

**Минусы:** промежуточный (частичный) текст отменённого ответа не попадает
в историю — модель при следующей задаче его не видит; отмена `edit_file`/
`write_file` посреди записи невозможна атомарно (сигнал проверяется до и
после вызова, не во время записи файла) — для мелких файлов это несущественно.

## Альтернативы

- **`agent.cancel()` вместо сигнала в run()** — отвергнуто: сигнал
  компонуется со стандартной AbortController-экосистемой (exec, fetch,
  readline.question) и явно привязан к одной задаче.
- **Событие `done` с флагом cancelled** — отвергнуто: терминальное событие
  без answer семантически другое; отдельный тип честнее для рендеров.
- **Персистентный allowlist (файл .agent/permissions.json)** — отложено:
  нужен аудит и UI просмотра/сброса; сессионный список — безопасный минимум.
