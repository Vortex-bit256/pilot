o# ADR 0004: Стриминг токенов и живой показ действий агента

- Статус: принято, реализовано
- Дата: 2026-08-06

## Контекст

Цикл агента ждал полный ответ LLM (`LLMProvider.chat(): Promise<LLMResponse>`):
при медленной генерации пользователь несколько секунд смотрит в пустой
терминал. Событийная архитектура (ADR 0001) уже отдавала `text`, `tool_call`,
`tool_result`, но CLI по умолчанию их не показывал — печатался только
финальный ответ. Задел под стриминг существовал: `ModelCapabilities.streaming`.

## Решение

1. **Протокол:** новое событие `text_delta { delta }`. Контракт: текст
   ассистента приходит либо одним событием `text` (не-стриминг), либо серией
   `text_delta` (стриминг) — никогда оба для одного сообщения. `done.answer`
   всегда содержит полный текст.
2. **Провайдер:** опциональный `LLMProvider.chatStream?(params)` — async-
   генератор `LLMStreamChunk`, возвращающий тот же собранный `LLMResponse`,
   что и `chat()` (tool calls, usage, stopReason). Цикл агента предпочитает
   стриминг, когда `config.streaming && capabilities(model).streaming &&
   chatStream` — иначе фолбэк на `chat()`. Провайдеры без стриминга метод
   не реализуют (open/closed).
3. **Tool calls наружу не стримятся:** id/name/arguments склеиваются из дельт
   внутри провайдера, событие `tool_call` остаётся цельным. Usage приходит
   в возвращаемом `LLMResponse` (у DeepSeek — через `stream_options.
   include_usage`), а не отдельным чанком.
4. **CLI:** живой рендер по умолчанию — токены в stdout по мере генерации,
   `→ tool args` / `← ok (N chars)` однострочниками, usage — dim'ом.
   `--debug` остаётся эталонным подписчиком: сырые события в stderr, финальный
   ответ в stdout (скриптабельно: `2>/dev/null`).
5. **Kill-switch:** `streaming: false` в `agent.config.json`, `AGENT_STREAMING=0`
   или флаг `--no-stream` — для сред, где SSE-стриминг ломается (прокси).

## Последствия

**Плюсы:** мгновенная обратная связь (время до первого токена вместо времени
полного ответа); процесс работы агента виден без `--debug`; протокол остаётся
сериализуемым — headless-сервер фазы 4 не затрагивается, события просто чаще.

**Минусы:** два пути доставки текста — каждый клиент обязан обрабатывать и
`text`, и `text_delta`; склейка tool_call-дельт — нетривиальный код в каждом
стримящем провайдере.

## Альтернативы

- **Заменить `chat()` на всегда-стрим с буферизацией в цикле** — отвергнуто:
  ломает существующий интерфейс и обязывает все провайдеры реализовывать
  стриминг; опциональный метод дешевле и обратно совместим.
- **Стримить `tool_call_delta` наружу** — отвергнуто: частичные аргументы
  (невалидный JSON) бесполезны клиентам и усложняют протокол и все рендеры.
- **Эмитить и `text_delta`, и итоговый `text`** — отвергнуто: клиентам
  пришлось бы дедуплицировать текст; контракт «либо-либо» проще.
